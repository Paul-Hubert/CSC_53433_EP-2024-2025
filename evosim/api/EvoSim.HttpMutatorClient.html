A mutator model behind a server (10 §2): one chat call per request with the prompt alone (CORE-07, MUT-11), the request's seed and temperature, thinking off. Calls run on the thread pool and fill the reply; the MutatorService caches answers and batches rounds (MUT-14, MUT-31).

Examples

A trimmed OpenAIMutatorClient:

public class OpenAIMutatorClient : HttpMutatorClient
{
    protected override string ChatPath => "/v1/chat/completions";
    protected override string HealthPath => "/v1/models";

    public override JObject Body(MutatorRequest r) => new JObject
    {
        ["model"] = r.Model,
        ["messages"] = UserMessage(r.Prompt),
        ["seed"] = r.Seed,
        ["temperature"] = HttpCaller.Number(r.Temperature),
    };

    protected override string Content(JToken response) => (string)response["choices"]?[0]?["message"]?["content"] ?? "";
}

Remarks

The MutatorService gets each mutation with its tries already drawn (MUT-30), looks each prompt up in its cache, and calls Send(IReadOnlyList<MutatorRequest>) on the main thread with the rest of a round. Send(IReadOnlyList<MutatorRequest>) returns a MutatorReply at once and posts every request from the thread pool, at most maxParallel at a time, with the time-out and tries of Caller (DEC-42). A request that still fails gets an error in the reply: the service then leaves the gene unchanged, and a strict service also stops the run (MUT-04).

To use another server, derive from it and give ChatPath, HealthPath, Body(MutatorRequest) and Content(JToken). The body holds nothing but the prompt as the user message (B-11): build it with UserMessage(string). Body(MutatorRequest) and Content(JToken) run on the thread pool, so they must not touch Unity objects. Place the component under the World, next to the MutatorService. The API key never goes in a field: apiKeyVariable names the environment variable that holds it (OUT-04).
